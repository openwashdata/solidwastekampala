# Add Alex Y. Katukiza's ORCID iD

Plan written 2026-07-28. Adds the ORCID iD
[0000-0003-1774-8237](https://orcid.org/0000-0003-1774-8237) for Alex Y.
Katukiza, the only author on `solidwastekampala` still without one, and
propagates it to the citation files and the pkgdown website.

## Context

Author metadata was completed in two earlier passes: #14 / PR #16 added the
five iDs that could be matched on the public registry, and #15 / PR #24
added Namagembe's, confirmed Feni's and Batte's, and corrected Batte's
spelling. Katukiza was left without an iD in both passes because no record
could be found. The main author has now supplied it.

After this change all eight authors carry an ORCID iD.

## Verification performed before editing

The public ORCID registry could not be reached from the working
environment: `pub.orcid.org` and `orcid.org` are refused by the egress
policy (403 on CONNECT), so the identity behind the iD was **not**
confirmed against the registry here. It rests on the main author's word,
which is the same source that resolved #15. Two offline checks were run
instead, both passing:

- ISO 7064 MOD 11-2 checksum over the 16 digits is valid, so the iD is not
  a typo.
- The iD does not duplicate any of the seven iDs already in the package.
  This matters: the iD first supplied for Namagembe in #15 duplicated
  Batte's and was rejected on that basis.

Whoever next runs the toolchain locally should open the record and confirm
it names Alex Y. Katukiza (Makerere University).

## Toolchain caveat

R is not installed in the working environment, so `washr::update_citation()`,
`washr::update_description()`, `devtools::document()`,
`devtools::build_readme()`, and `pkgdown::build_site()` cannot be run. The
generated files are therefore edited by hand, each edit shaped to match
exactly what the generator produces, using the corresponding hunks of PR #24
(commit `0f255c0`) as the reference for every file's house style.

This is a deviation from the CLAUDE.md rule that citation files are
regenerated with washr after an author change. Re-running the commands
locally is expected to be a no-op; it is listed under Verification below so
that any drift is caught.

## Files to change

Source of truth:

1. `DESCRIPTION` — add `comment = c(ORCID = "0000-0003-1774-8237")` to the
   Katukiza `person()` call, wrapping to a second line at 80 characters in
   the style of the other authors.
2. `CITATION.cff` — add `orcid: https://orcid.org/0000-0003-1774-8237` after
   `given-names:` in the Katukiza block (field order: family-names,
   given-names, orcid).
3. `inst/CITATION` — add the same `comment = c(ORCID = ...)` argument to the
   Katukiza `person()` inside the `bibentry()` author vector.

Website (`docs/`, normally regenerated by pkgdown):

4. `docs/authors.html` — add the ORCID anchor and `fa-orcid` icon span to the
   Katukiza list item, matching the other seven entries.
5. `docs/authors.md` — add the `[](https://orcid.org/...)` line under the
   Katukiza entry.
6. `docs/index.html` — add the same anchor to the Katukiza entry in the
   sidebar author list.

## Files deliberately not changed

- `data-raw/metadata/creators.csv`, `data-raw/metadata/dataspice.json`,
  `inst/extdata/metadata.json`: the dataspice creator schema in use here
  carries only name, affiliation, and email. No author has an ORCID in these
  files, so adding one only for Katukiza would be inconsistent, and
  `write_spice()` would drop a hand-added field on the next run. Adding
  ORCIDs to the dataspice metadata for all eight authors is a worthwhile
  FAIR improvement, but it is a schema change and belongs in its own issue.
- `README.Rmd` / `README.md`: the rendered citation block prints author
  names without ORCIDs, so there is nothing to update.
- `docs/index.md`, `docs/llms.txt`: no author list.
- `docs/search.json`: the ORCID appears only as an icon link with no text
  content, so the search index is unaffected.
- `man/`, `R/`: no author metadata.
- `NEWS.md` and the version: see below.

## Version and release

The version stays at 1.0.0 and no release is cut. This is a post-release
metadata correction, so the GitHub state will differ from the archived
Zenodo deposit for `10.5281/zenodo.21519797` until a new version is
released. Bumping to 1.0.1 would touch the version string in DESCRIPTION,
both citation files, and roughly a dozen generated pages under `docs/`, all
by hand and without the toolchain to verify them, and cutting a Zenodo
deposit is an outward-facing publishing step. Both are left as an explicit
decision for the maintainer, who can run `/create-release 1.0.1` with R
available.
